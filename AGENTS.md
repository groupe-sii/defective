# AGENTS.md

Sample from the AWS Strands Agents SDK, reworked into a **multichannel conformity-assistant** demo: a field technician reports an equipment non-conformity over WhatsApp **or SMS**, the Strands agent searches past Non-Conformity Reports in a Bedrock Knowledge Base, drafts a handling procedure, and an approved procedure is "emailed" to the contractor (mock). Flow: inbound message → AWS End User Messaging → SNS → one Lambda running a Strands agent on Bedrock → reply on the same channel. Two chat roles: `technician` (everyone) and `expert` (numbers in the `ExpertContacts` parameter) who validates the draft in their own 1:1 chat. Outbound email/RCS are dispatched but stubbed/mocked (Phase 3).

## Layout (first-party code is only under `lambdas/`)

- `lambdas/lambda_function.py` — Lambda entrypoint (`lambda_function.lambda_handler`). Parses SNS records, normalizes each into an `InboundMessage` (`utils/messages.py`), resolves the sender's role (`resolve_role` vs `EXPERT_CONTACTS`), sets per-invocation sender context (`tools.context`), loads per-identity history from DynamoDB (sanitizing `Decimal`s — see Conventions), invokes the agent with a `[Session] sender_role=...` line, strips `<thinking>...</thinking>` blocks, and dispatches the reply via `utils/dispatcher.py`.
- `lambdas/utils/messages.py` — **inbound normalizer**: `parse_sns_message` detects the envelope (`whatsAppWebhookEntry` vs SMS `originationNumber`/`messageBody`) and returns `InboundMessage(channel, sender, text, message_id, recipient, ...)`. `identity` is the digits-only canonical key.
- `lambdas/utils/dispatcher.py` — **outbound dispatcher**: `send_reply(channel, sender, text, **meta)` → `_send_whatsapp` / `_send_sms` (pinpoint-sms-voice-v2) / `_send_email` (SES v2) / `_send_rcs` (stub). Honors `MOCK_CHANNELS`.
- `lambdas/strands_agent.py` — wraps `strands.Agent`; rebuilds the agent with stored `messages` + `system_prompt` when history exists, else builds a fresh agent from `utils.locales.MESSAGES` + the session line. Tool list lives in `AGENT_TOOLS`.
- `lambdas/tools/` — Strands `@tool` functions: `ncr.py` (`search_ncr_history`, Bedrock KB `Retrieve`; falls back to image-caption metadata since the KB is currently image-only), `case.py` (case lifecycle in DynamoDB: `create_case` / `get_case` / `list_cases` / `record_validation`; the last one is expert-gated via `tools.context`), `mail.py` (`send_contractor_email`, approval-gated, `MOCK_EMAIL=true` logs instead of sending), `notify.py` (`request_expert_validation`, mock ping), `context.py` (per-invocation sender role/identity/channel — set by the Lambda, read by tools; not a Strands tool).
- `lambdas/utils/whatsapp.py` — WhatsApp webhook parsing (`WhatsappService`, `WhatsappMessage`). The reply send moved to `dispatcher.py`; this file is now parse-only.
- `lambdas/utils/` (rest) — `dynamo.py`, `locales.py` (system prompts for both roles in `en_US` / `pt_BR` / `fr_FR`, + error strings).
- `template.yaml` — all infra: IAM role, Lambda, SNS topic, 2 DynamoDB tables (`WhatsAppUserHistory`, `NonConformityCases`), customer-managed KMS key. Stack name is fixed: `aws-whatsapp-stack`.
- `pack_lambda.sh` — builds `lambda.zip`: resolves deps for linux with `uv pip compile --python-platform linux` (→ `req-linux.txt`), installs them into `package/` with `pip --no-deps` + manylinux wheels, copies `lambdas/*` on top, zips. `pack_and_deploy.sh` calls it; it `rm -rf package` first, so builds are always clean.
- `mock_send.py` — demo driver for mock mode (see Commands): publishes a fake inbound event (WhatsApp webhook or SMS envelope) to the stack's SNS topic, then tails CloudWatch Logs for the agent's reply. Needs local AWS credentials; `--print-event` works offline without any.
- `package/`, `req-linux.txt`, `lambda.zip` — **build artifacts** (gitignored), not source. Never edit files inside them.

## Commands

- **Build**: `./pack_lambda.sh [python-version]` → `lambda.zip`. Needs bash, `7z`, `pip` on PATH, and `uv` (without uv it falls back to plain pip — only safe on a Linux host; see the header comment for the Windows packaging trap it exists to avoid). `pack_and_deploy.sh` runs it for you.
- **First deploy**: `./pack_and_deploy.sh <s3-bucket> <s3-key> [python-version]` (default `3.11`). Needs bash (Git Bash/WSL on Windows), aws CLI with a region configured (`aws configure get region`), `7z`, `uv`, and a pre-existing S3 bucket. Uploads `lambda.zip`, then runs `aws cloudformation create-stack` — so it **fails against an existing stack**.
- **Redeploy** (stack exists): rebuild, upload `lambda.zip` to a **new prefix** (e.g. `assets/r5`), then:
  `aws cloudformation update-stack --stack-name aws-whatsapp-stack --template-body file://template.yaml --parameters ParameterKey=S3BucketName,ParameterValue=<bucket> ParameterKey=S3BucketPath,ParameterValue=assets/r6 ParameterKey=PythonVersion,ParameterValue=python3.11 ParameterKey=LocaleConfig,ParameterValue=en_US ParameterKey=FoundationModelParam,ParameterValue=eu.amazon.nova-pro-v1:0 ParameterKey=MockChannels,ParameterValue=whatsapp,sms,email,rcs ParameterKey=KnowledgeBaseId,ParameterValue=GXY5L19KJX ParameterKey=ExpertContacts,ParameterValue=5511999998888 ParameterKey=MockEmail,ParameterValue=true --capabilities CAPABILITY_IAM`.
  The prefix **must change**: CloudFormation only calls `UpdateFunctionCode` when the computed `S3Key` differs — re-uploading over the same key is a silent no-op (code is currently deployed from `assets/r5`). Safe alternative to blind `update-stack`: create + inspect + execute a change set first. Or `./destroy.sh` first (deletes only the stack; the S3 bucket is yours).
- **Demo without a phone number (mock mode)**: the `MockChannels` parameter (default `whatsapp,sms,email,rcs`) is a CSV of channels answered in demo mode. A channel in the list **logs** the reply (`MOCK_<CHANNEL>: reply to <identity>: ...`) instead of sending; a channel removed from the list is sent for real and must be provisioned (see Phase 3). Each channel flips independently. `MockEmail=true` is a separate, finer flag that makes `send_contractor_email` log (`MOCK_EMAIL case=... to=...`) instead of sending via SES, regardless of `MockChannels`. Drive it end-to-end with `.venv/Scripts/python mock_send.py "message" --phone <number> --channel whatsapp|sms` (publishes a fake inbound event to the stack SNS topic, prints the reply from `/aws/lambda/WhatsApp-Aws-Integration-Main`); flags: `--phone` (reuse a number to demo shared history; also picks the role — `5511999998888` is the default expert), `--channel` (whatsapp webhook or SMS envelope), `--text`, `--print-event` (offline), `--tail-only`. The full non-conformity flow is verified: technician reports → KB search + `create_case` + `request_expert_validation` → expert `--phone 5511999998888` approves via `record_validation` → technician asks status → technician requests email → `MOCK_EMAIL` logged, case row ends `CONTRACTOR_NOTIFIED`. Cross-channel continuity is verified too: a message sent by SMS from the same number sees the WhatsApp conversation (history is keyed by identity, not channel). Set a channel's `MockChannels` entry to `false`/remove it once that channel is really provisioned (for WhatsApp that's also when the README's Event Destination console step matters); set `MockEmail=false` only once an SES identity exists.
- Locale and model are **not** passed by the deploy script — they come from defaults in `template.yaml` (`LocaleConfig: en_US`, `FoundationModelParam: eu.amazon.nova-pro-v1:0`, `MockChannels: whatsapp,sms,email,rcs`). Edit `template.yaml` before deploying to change them.
- There is **no** test, lint, format, typecheck, or CI config in this repo — don't go looking for `pytest`/`ruff`/workflows. Note `.gitignore` ignores `tests/`, so any tests you write won't be committed unless you un-ignore that path.

## Smoke-checking code locally

Env vars are read at **module import time** (`LOCALE`, `DEFAULT_MODEL`, `USER_HISTORY_TABLE`, `CASES_TABLE` — normally injected by the Lambda config in `template.yaml`), and `tools/case.py` + `tools/ncr.py` build boto3 resources/clients at import time. So importing the Lambda code needs both env vars and resolvable AWS credentials (dummy access keys are enough — no network call happens):

```bash
cd lambdas
LOCALE=en_US DEFAULT_MODEL=eu.amazon.nova-pro-v1:0 \
USER_HISTORY_TABLE=WhatsAppUserHistory CASES_TABLE=NonConformityCases \
AWS_ACCESS_KEY_ID=x AWS_SECRET_ACCESS_KEY=x AWS_DEFAULT_REGION=eu-west-1 \
../.venv/Scripts/python -c "import lambda_function"
```

Verified working from this repo (Python 3.11 `.venv`; README also documents a plain venv + `pip install -r requirements.txt` — both target 3.11).

## Dependencies: two files, keep in sync

- `requirements.txt` is what actually ships in the Lambda: installed with `--platform manylinux2014_x86_64 --only-binary=:all:`, so every runtime dependency must have manylinux wheels (pure Python is fine). Anything you add for Lambda runtime goes here. Pinned `strands-agents>=1.61.1` deliberately — older pins let the Windows packaging fallback silently resolve to 1.1.0.
- `pyproject.toml` + `uv.lock` are for local dev only. Update them alongside `requirements.txt` when adding a runtime dependency.
- `[dependency-groups] dev` in `pyproject.toml` holds local-only tooling: `botocore[crt]`, which boto3 requires when credentials come from `aws login` (otherwise: "Using the login credential provider requires an additional dependency"). `uv sync` installs it; `mock_send.py` needs it.
- `boto3` is deliberately absent from `requirements.txt` — the Lambda runtime provides it (and `uv.lock` pulls it in transitively via strands-agents).
- `req-linux.txt` is generated by `pack_lambda.sh` on every build (gitignored) — never hand-edit it.

## Conventions that differ from defaults

- **i18n lives in two places**: `utils/locales.py` (system prompts for both chat roles + unsupported-type error) and the `LocaleConfig` values in `template.yaml`. Supported values today are `en_US`, `pt_BR` and `fr_FR`.
- **Role gating is code, not prompt**: `lambda_function.resolve_role` compares the sender against the `EXPERT_CONTACTS` parameter and stores the result in `tools.context` for the duration of one message (set before the agent runs, cleared in `finally` — Lambda containers are reused). `record_validation` refuses non-experts there; the system prompt's role instructions are a second, softer layer.
- **History replay needs `Decimal` sanitizing**: DynamoDB returns numbers as `decimal.Decimal`, and Strands re-validates stored `toolUse` inputs on replay — `Decimal` fails the JSON-schema check (`Invalid type for document parameter ...`). `lambda_function.sanitize_decimals` converts history numbers back to int/float before handing it to the agent. Any new tool with numeric arguments will break replay without this.
- The SNS topic's customer-managed KMS key is **required**, not optional: AWS End User Messaging can't publish through the AWS-managed `alias/aws/sns` key (see comment in `template.yaml`). Don't remove or swap it.
- Conversation history: one DynamoDB row per identity + day in `WhatsAppUserHistory` (keys `phone_number` / `day`, day format `%Y/%m/%d`). `phone_number` holds the **channel-agnostic identity** (digits only, no `+` — `utils/messages.normalize_identity`), so the same number on WhatsApp and SMS shares one conversation; `channel`, `recipient`, `message_id`, `channel_meta` are stored as per-row metadata. Replay uses the stored `messages` and `system_prompt` (which already embeds the `[Session] sender_role=...` line, so a role change mid-day would need a history purge). The IAM policy references a GSI `PhoneNumberDayIndex` that the template never creates — `DynamoDB.query_with_gsi` is dead code; don't rely on it without adding the GSI.
- **Multichannel = normalize in, dispatch out**: `utils/messages.parse_sns_message` detects the envelope (`whatsAppWebhookEntry` vs SMS `originationNumber`/`messageBody`) and returns `InboundMessage`; `utils/dispatcher.send_reply(channel, ...)` sends (or mocks) on the matching channel. Adding a channel means a branch in each of those two files — no changes to the Lambda, agent or tools.
- Non-conformity cases: `NonConformityCases` table, PK `case_id` (e.g. `NC-YYYYMMDD-xxxxxx`), GSIs `created_by-index` and `status-index` (both `ProjectionType: ALL`). Lifecycle `PENDING_VALIDATION → APPROVED|REJECTED → CONTRACTOR_NOTIFIED`, written via put_item of the whole item.
- **The KB (`GXY5L19KJX`, `hackaton-nci`) is currently image-only**: `Retrieve` returns `byteContent` PNGs whose captions live in the `x-amz-bedrock-kb-description` metadata key. `tools/ncr.py` never surfaces base64 — it returns the caption as `summary` with `modality: image`. Once real text NCRs are ingested the same tool returns `modality: text` with no code change.
- Only `text` WhatsApp messages are handled; anything else returns the locale error and a 500.
- Bedrock: the default model is `eu.amazon.nova-pro-v1:0`, an inference profile matching the stack's region (`eu-west-1`) — `us.*` profiles are rejected there with `ValidationException` (verified). Model access must be enabled in `eu-west-1`.
